# CLAUDE.md — Project Instructions for Claude Code

## Who this is for
Dinesh Parmar, entrepreneur based in Vadodara/Surat, Gujarat. Runs Book N Fly (travel agency), Scale Visory (accounting/tax/legal advisory), ZYNTA Placement Services (recruitment), Arth Advisory (formerly Artha Bad Debt Recovery), and Arrohan Living (furniture/interior). Wants a personal task assistant that reads his WhatsApp and manages tasks/reminders.

## Project goal
Build a personal assistant that:
1. Connects to Dinesh's **personal WhatsApp** (not just a business number)
2. Reads incoming messages automatically
3. Extracts actionable tasks from them using AI (task, due date, priority, source contact)
4. Stores tasks in a simple task manager / dashboard
5. Organizes them (open/done, priority, due date)
6. Sends reminders back on WhatsApp for due/overdue tasks
7. Eventually needs a mobile-friendly way to view/manage tasks (PWA, not a native app — see "Mobile" section below for why)

## Current state — what's already built

Located at `/wa-task-assistant/` (backend + frontend). Rebuilt in-repo from this spec; see `wa-task-assistant/README.md` for the full run/deploy guide.

### Backend (Node.js + Express)
- `whatsapp-web.js` for the WhatsApp connection — QR-code login (like linking a device), NOT the Meta Business Cloud API. This matters: Business API can only see messages sent TO a business number. Dinesh wants his personal chats read, which requires the WhatsApp Web session approach instead.
- Incoming messages get buffered (~15s of quiet) and batch-sent to **Claude (Anthropic API, model `claude-sonnet-4-6`, overridable via `ANTHROPIC_MODEL`)** with a system prompt that extracts `{title, description, contact, chat_name, due_date, priority}` as JSON. Ignore casual/non-actionable messages.
- **SQLite** (`better-sqlite3`) for storage: `messages` table (raw incoming messages) and `tasks` table. A task carries `status` (**open / in_progress / done**), `priority`, `due_date`, `remind_at`, and `origin` (**ai** when the extractor made it, **manual** when it was typed by hand or parsed by `quickparse`). `origin` was added later and back-filled from `source`, so nothing was lost. Anything not `done` still counts as owed: reminders, the digest and the Open view all read `status != 'done'`.
- **node-cron** job runs twice daily (8:30 AM & 6 PM IST) — sends a WhatsApp digest of every open task that is due, overdue, or undated, back to Dinesh's own number. Reminders **repeat every run until the task is marked done**; each send bumps `reminder_count`, which the digest and dashboard show as "asked 4x" / "reminded 4×".
- REST API (`/api/tasks` — GET/POST/PATCH/DELETE) for the dashboard to read/write tasks.

### Frontend (React)
- Laid out as an **application shell**: a fixed left sidebar (Dashboard, My Day, All Tasks, By Chat, AI Tasks, Calendar, Completed, Settings) beside a main column whose top bar carries search with Ctrl-K, notifications, refresh and the linked WhatsApp account. Then a greeting with a New Task button, four KPI cards with tinted icons, a quick-actions card, and **tasks on the left with a summary rail on the right**. Every sidebar item drives the *same* board state — it is navigation over one list, not a second application. Polls every 30s.
- **Settings is its own section**, holding the connection status, the linking QR, the diagnostics block, the AI self-test and the blocked-chats panel. Those used to sit above the task list on every page load; moving them here is what keeps the dashboard clean, and a banner offers a way back when WhatsApp is not connected.
- Icons are **one inline SVG set** (`components/Icon.jsx`) on a 24px stroke grid — no icon font, no dependency, nothing borrowed from elsewhere.
- Below 1180px the sidebar becomes a drawer behind a menu button; below 1080px the rail folds under the board; below 760px everything is one column with a **fixed bottom navigation bar** (My day · Open · + · All · Summary), which is what makes it read as an app on a phone.
- Above the list sits **Focus today**: the two or three tasks that most need attention, ranked overdue → high priority → due today → in progress, taken from the real list; with nothing qualifying it says so rather than showing an empty frame.
- Tasks are **collapsible sections separated by rules and whitespace**, not cards inside cards — Overdue, Today, Tomorrow, This week, Later, No date — switchable to **one section per chat**. A row is a title, a plain-text due date, and a quiet meta line (chat, AI-or-manual, priority), with everything else behind a **⋮ menu** (Start, Due today, Due tomorrow, Details, Delete) that appears on hover and stays visible on touch. Descriptions that merely restate the title are suppressed, in the UI and in the extraction prompt.
- The **summary rail** carries today's figures, a progress bar, a compact month calendar (dots on days with work; clicking one scopes the board to that date), upcoming counts, the WhatsApp/AI state, and recent activity. **Every figure is derived from the loaded tasks** — no placeholder numbers. Recent activity is built from `created_at` and `completed_at`, the only history the app actually records; an edited due date leaves no trace and so is not claimed. A day with nothing scheduled says so rather than showing 0%.
- The **design system** is deliberately plain, but the ground is not flat: a warm linen tone that deepens down the page, under a faint SVG grain, so the white cards read as sheets laid on a surface. The top bar is a **sticky full-width white band** (search stays reachable while scrolling); the task list is one sheet with hairline-separated sections. 4–8px radii, hairline borders, near-zero shadows, one teal accent held back for state, status colour only as a signal. Self-hosted Archivo + IBM Plex Sans/Mono; verified in light and dark.
- **Task detail** opens as a side sheet (a bottom sheet on a phone): title, notes, status, priority, due date and time, reminder preset, and the facts — created, updated, completed, AI-created vs added by hand, the WhatsApp chat, and an expander for **the one original message** that produced the task (joined by `message_id`; no other chat content can reach the client).
- **Search** across title, notes, chat, contact and the source message; a **filter popover** for status, priority, source and chat; and a **My day** view that ranks overdue → in progress → high priority → due today. All of it is applied client-side over one `?status=all` fetch, so switching views costs nothing.
- The connection/pipeline detail collapses to a single line when everything is healthy, and opens itself when something needs attention (not connected, missing API key, a failed extraction, or messages arriving but not being kept).
- Plain CSS in `src/styles.css`, no UI framework. Self-hosted Archivo + IBM Plex Sans/Mono in `public/fonts/` (186 KB, works offline — the same faces as the demo and deploy artifacts, so all three read as one product). Priority is a coloured spine on the card rather than another chip. All text meets WCAG AA in both themes, verified in a browser.

### Two capture modes (`EXTRACTION_MODE`)
Dinesh asked what the product looks like without Claude, citing cost, third-party dependency, privacy, and possibly reselling it. A keyword-based extractor was measured against held-out Hinglish messages and scored 33% recall (missed two real tasks in three), so it was **not** built. Instead there are two honest modes, switchable by env var:
- **`ai`** (default) — Claude reads all incoming chats. Ambient, best quality, ~₹275/month at 100 msgs/day.
- **`manual`** — no AI, no API key, zero cost. Tasks come only from messages Dinesh writes or forwards to his own "message yourself" chat, or any message prefixed with `TASK_TRIGGER` (default `#task`). `quickparse.js` does deterministic date/priority parsing on his own words. Other people's messages are never read and the `messages` table stays empty, which is the privacy answer.

He asked to see both before choosing, so both ship and the dashboard shows which is active.

### Security hardening
- **Brute-force lockout** — 5 failed attempts from an address locks it out for 15 minutes; a success resets the counter. `trust proxy` is set so Railway's balancer isn't counted as one client.
- **helmet** with a CSP that allows same-origin only plus the `data:` URL the linking QR needs, `frame-ancestors 'none'`, HSTS, nosniff, no `X-Powered-By`.
- **Errors leak nothing** — client errors keep their status (400/413) with a generic message; unexpected errors are a bare 500 with the detail logged server-side.
- Failed attempts logged; `/api/status` reports locked-out addresses. 100 kB body cap. Loud boot warning when `CORS_ORIGIN` is unset.
- **Still weak, deliberately deferred:** session file and SQLite unencrypted at rest, one shared password with no 2FA, token in `localStorage`.

### Reply commands, blocked chats, exact-time reminders
- **In `ai` mode your own messages are read too.** One `message_create` listener covers both directions, so a note you type into any chat ("Do bnf salary by today") becomes a task the same way an incoming request does. Reply commands are checked first so `done 2` stays an instruction. Earlier this mode listened to `message` only, which silently ignored everything Dinesh wrote himself - which is how he actually records tasks.
- **Reply on WhatsApp** — every digest line is numbered. `done 2`, `done 1,3`, `done all`, `2 ho gaya`, `kar diya 3`, `snooze 2`, `snooze 2 3`. Works in both modes; only counts in the digest chat. The parser refuses sentence-shaped text so *"invoice ka kaam done karna hai"* stays a message. `commands.js` + `handleCommand()`.
- **Blocked chats** — `blocked_chats` table, dashboard panel, `/api/blocked-chats`. In `ai` mode a blocked chat is dropped *before* anything is stored or sent to the API. **Two checks, after a real leak**: the block test read `chat?.name` alone, and `getChat()` fails often enough (Meta-hosted business chats, contacts that will not resolve) that a message the row filed under "CYBER CHATHAN" was tested against `undefined` and kept — reported as "blocked, still arriving". Now an early cheap check on the id runs *before* a photo is downloaded or a voice note transcribed, and the full check tests every name the row is built from plus the id at the right end (`message.to` on his own messages, not `from`, which is himself). **A block is about a CHAT, never a person.** In a group only the group's own name and id are tested — the sender's name and number are on the message too, and testing those made blocking a person follow him into every group he writes in, which would lose real work. In a one-to-one chat the person *is* the chat, so the contact's name and number are tested there (that is the case that leaked). So: blocking a group silences that group and nothing else; a member of a blocked group still gets through in his own chat and in other groups. **Blocking a group blocks everyone in it**; where the chat lookup fails, the group's name is fetched by id *before* the check, because that is the name the row would otherwise be stored under. `backend/tests/blocking.test.mjs` (12 cases) reproduces both leaks and pins the not-a-person rule — 2 of 7 fail on the old check, 1 more on the un-hoisted group lookup. Names match loosely (`Mummy` catches `Mummy ❤️ Home`); numbers match on their ending, and a numeric pattern under 6 digits is refused rather than blocking half the contacts. Dinesh chose the blocklist shape over an allow-list.
- **"I blocked these yesterday, why are they still there?"** — the AI Usage list covers **30 days**, so a chat blocked yesterday still shows every message it cost *before* the block. That is indistinguishable from a block that is not working, so the page now answers it directly: a **Blocked chats** panel splits each pattern into what it cost **before** and what has been read **since** it was added. In `ai` mode a blocked chat is dropped before anything is stored, so a working block reads **0 since, for ever**. Three states, each with the fact behind it: *still arriving* (names the chat), *nothing since* (the count it cost before), and **never matched a message** — the commonest and least visible failure, where the name on the list is not the name the messages are filed under; there it names the nearest chat that does exist (*"did you mean 'Sai Samarth Residency'?"*). `blockEffect()` in `db.js`, 6 more cases in `blocking.test.mjs`.
- **The blocks were not firing because of spacing.** Seven chats blocked one evening, and the next day the counts were still climbing. A name typed by a person is not the name WhatsApp files the chat under: `shubham prajapati` vs **`shubhamprajapatis747`**, `saisamart` vs **`Sai Samarth Residency`**. A literal substring test says no to both, so the block silently never fired — and the panel above would only have said "never matched a message". Matching now **flattens spacing and punctuation on both sides** (`flatten`): the letters must still all be there, in order, so nothing new gets caught, but a human spelling of a chat's name now works. All four of his patterns match under the new rule and none did under the old one.
- **A whole chat id now matches the id.** A pattern like `120363…@g.us` or `89309717786799@lid` is not all digits, so it was tested against the chat's *name*, where an id never appears — and the one time you have only an id is a group WhatsApp has not named yet, which is exactly when you want to block it.
- **The blocklist panel shows each block's effect** (still arriving / nothing since / never matched, with the nearest real chat name and a "Block that instead" button), a chat already covered by a pattern **leaves the tap-to-block list** (the server marks it, by the same rule), and typing a name nothing matches now warns that blocking it stops nothing rather than encouraging it.
- **"57 still arrived after you blocked it" was true and useless on its own.** A block added last night, with the matching fixed this evening, is *supposed* to have a large number behind it — every one of those arrived while the check could not match the name. What says whether it is fixed is a different figure: **has anything arrived since the running version came up.** `blockEffect` takes the process's `startedAt` and reports `sinceBoot` beside `since`, so the panel reads *"51 got through before the last restart — none since"* (fixed) rather than the same red number as *"5 arrived since the app restarted"* (a live leak, with the time of the last one).
- **The leak the blocklist could not close on its own: a group whose name had not arrived yet.** `getChat()` fails, the row is stored under the chat **id**, the block is written against the **name** — so it matches nothing and every message is read and paid for. Later `applyGroupName` learns the name and rewrites the row, and only then does the block appear to have been leaking. Now, the moment a repaired name matches the blocklist, **that chat's id is added to the list too** — not a wider block (an id names exactly the one chat whose name is already blocked) and, unlike a name, it cannot fail to resolve again. The panel also offers *"Block its id too"* on any leaking group. 9 more cases in `blocking.test.mjs`.
- **"Why this blocked msg restarted?"** — every row read *"58 got through, none since the restart"* against a moment the page never named. The restart is the app process coming up, and **it restarts on every deploy** — so that one sentence covered four days of proof and four minutes of nothing equally well, which is a figure without its basis. Both panels now carry `bootedAt` from the server and say the span: *"177 got through, none in the 3 days since the restart"*, and the blurb states outright that it restarts on every deploy and that restart is the clock these figures run on. Under two hours it says so instead of implying a clean bill — *"that is not long enough to prove much yet; these chats may simply not have written. Worth another look tomorrow."* 4 more cases in `blocking.test.mjs`, including that every route reporting a block also reports the restart.
- The matching rule now lives in **one place** (`src/blocklist.js`, `matchesPattern` / `patternWouldDrop`): the listener decides with it and the panel explains with it, because an explanation built on a second copy would eventually lie. The panel applies the chat-not-a-person rule too — a blocked person's messages inside a group are correctly counted as *not* blocked.
- **Exact-time reminders** — `remind_at` on tasks, fired by a separate cron (`EXACT_REMINDER_CRON`, default every 5 min), independent of the twice-daily digest. Times parsed from `10 baje`, `5 baje shaam`, `at 5pm`, `5:30 pm`, `17:00`; a bare 1–7 reads as evening. Both `quickparse.js` and the Claude schema produce it.

### Reminder and follow-up engine
The engine chases **Dinesh about his own tasks**. There is no notion of chasing a customer; an earlier pass built that and it was wrong.
- **`tasks.due_at`** is the deadline (migrated from `remind_at`, which had been holding the clock time parsed out of messages). A date with no time uses `defaultDueTime`, read in `TIMEZONE`.
- **The ladder**: one reminder `defaultReminderOffset` before the deadline, one at it, then follow-ups at `followUpOffsets` (default 30 min / 2 h / 16 h after) while the task is still not done. After `followUpMax` the task is flagged **needs attention** and the app stops asking — the difference between reminding and spamming.
- **Only ever one rung is scheduled ahead.** The next is arranged when the current one fires, so a task that gets finished never has a queue of nagging behind it. A rung that has already elapsed keeps its intended distance from when the previous one actually went out, so a long-overdue task does not get three notifications in a minute.
- **Duplicates are impossible twice over**: a partial unique index on `(task, kind, round)` means asking for the same reminder returns the existing one, and delivery claims a row with a conditional `UPDATE ... WHERE status IN ('scheduled','snoozed')` — exactly one caller can win, so a second tick, a restart mid-send or a retry sends nothing.
- **Completion ends everything.** Marking done cancels every pending row and the engine skips finished tasks in both halves of its pass. Rescheduling clears the schedule, resets the escalation count and rebuilds the ladder from the new deadline.
- **State is derived, not stored**: status stays open / in_progress / done, and due / overdue are a function of the deadline and the clock, so there is no column for a job to keep correct.
- **WhatsApp control**: "BNF salary done" marks it done, "sunshine audit kal karunga" reschedules. `task-matching.js` scores word overlap in both directions and returns nothing when two tasks tie or nothing clears the threshold — acting on the wrong task is worse than not acting. Imperatives ("complete kar dena") are not completion reports. The same matcher stops the extractor creating a second copy of a task that already exists.
- **The duplicate guard was being defeated by the description.** Two identical "Activate Uttarakhand GST" rows, two "File GSTR-1", reported as *"why duplication?"*. `score()` is the weaker of its two directions, and the incoming title was scored against the existing task's **title *and* description** — so every word written on a task made that task *harder* to recognise: 3 title words shared out of 13 scored **0.23** against a threshold of 0.7, and a perfect copy was created. It now scores against the title alone as well and takes the better reading (`bestScore`): a description is more information about the same job and can only help identify it. `duplicateGroups` reads from both sides for the same reason — probing with title+description found a pair only on the second pass, from the copy that had no description, and then offered the **newer** row as the one to keep, losing the history "keep the oldest" exists to protect.
- **A lone digit is the whole identity.** `words()` dropped single-character tokens, so `GSTR-1` and `GSTR-9` both reduced to `gstr` and scored a perfect match — the annual return would have been **silently suppressed** as a copy of the monthly one. Single digits are kept now; single letters are still noise. `file` / `filing` / `submit` / `upload` joined the noise list, so "File GSTR-1" and "GSTR - 1" are recognised as one job.
- **The bar for merging rose from 0.7 to 0.8, and refusing to merge is the safe error.** At 0.7, *"Review Santosh Textile ledger scrutiny FY2025-26"* and *"Review Parth Bajaj ledger scrutiny FY2025-26"* scored 0.71 — five shared words out of seven — and one client's work would never have been created. A duplicate is visible and removable in two taps; a task suppressed by mistake is invisible for ever. `duplicateGroups` keeps the looser 0.7, because it only *offers* copies to a person: **strict when deciding alone, loose when asking.**
- **A name answers *who*, not *what* — and two tasks that agree on nothing else are not one job.** *"Ek hi kaam nahi, alag alag purpose he na."* Two "Talk with Vikas Gupta" rows were two conversations days apart about different things; the title never said which, so the app called them copies. Now `subjectWords(title, contact)` strips the person out of the title, and **a title that reduces to nothing but the person can never be merged and is never offered for review** — refusing costs a visible duplicate row, merging costs the second conversation, which is invisible. `talk` / `call` / `meet` / `discuss` / `speak` / `contact` / `regarding` / `about` / `with` joined the noise list: reaching somebody is not the job.
- **The real fix is upstream: the title must carry the purpose.** The extraction prompt and the schema now require the subject — *"Talk with Vikas Gupta about the Sena GST refund"*, never *"Talk with Vikas Gupta"* — and say to use whatever the message does give (an amount, a company, a form number) when it never states the subject outright.
- **For the vague titles already on the list, the tidy-up pass got the one thing it was missing**: the original WhatsApp message, sent only for titles with no subject (so a merely misspelt title costs what it always did). The prompt's hard rule is that the subject comes from the message and nowhere else — a title left vague is better than one with an invented purpose, because he will act on it. `backend/tests/titles.test.mjs` (3 cases), 5 more in `duplicates.test.mjs`.
- **THE ROOT CAUSE, found on the third report of it: the app was reading its own reminders back in.** *"Why again and again duplicate task coming"* — and the copies were stamped **6:01 PM** and **5:00 PM**, one minute after the six o'clock digest and on the hour the deadline reminder goes out. Everything this app sends goes to his own chat, from his own account, so WhatsApp reports it through `message_create` as **`fromMe`** — which is exactly what a note he typed to himself looks like, and a note he typed to himself is *deliberately* read as a task. So the evening digest, which lists every task still open, was read back a minute later and **every line of it made a second copy of the task it was reminding him about. Every evening. For every task.** The duplicate guard was the only thing standing between that and an endlessly doubling list — and the guard was broken by the description bug above, which is why it surfaced when it did. It also meant every reminder was paid for twice: once to send, once to read.
- `sendMessage` now remembers what it sent — **the text before the send** (because `message_create` can fire before `client.sendMessage` resolves) and the message id once WhatsApp gives one — and `handleMessage` drops anything that matches, at the one door every path goes through, catch-up included (a reconnect is exactly when the last digest is still sitting unread). Entries expire after ten minutes: this only has to survive a round trip of milliseconds, not filter everything he might ever type twice. Counted as **`echoesIgnored`** and shown in the connection panel as *"Own reminders ignored"*, because zero is the healthy figure and a rising one is a loop. `backend/tests/echo.test.mjs` (7 cases).
- **"The pending-task message it sends me — is it adding that list back as tasks again?"** The right question, asked of exactly that bug. The guard answers it, but the figure reporting the guard was this process's own count — and the app restarts on every deploy, so it read **0 nearly all the time, which is indistinguishable from a guard that is not running**. `echoes_ignored` is a persistent counter now (`meta`, like `own_messages_seen`), the status route reports `echoesEver` beside `echoesIgnored`, and the panel reads *"3 since start · 214 all time"*. A number he can look at is the answer; a zero that means "not this hour" is not. 2 more cases in `echo.test.mjs`.
- **The fix stops new copies; it cannot remove the old ones.** Reported again the next evening as *"still duplicate"* — and every pair on screen was created on 8–10 Sep, before the fix shipped. Both pairs (*Talk with Vikas Gupta*, *Call regarding remittance discussion*) group correctly on the Duplicates page and would now be refused at creation. What was missing was a way to clear them at the speed they accumulated: the page has a **"Merge the N with identical titles"** button, which acts only where the titles match character for character (`flatten`) — where a word count is enough to *ask* but not to act, the pair is still left for a person to read. Pressing a button nineteen times is why the page did not get used.
- The count also sits on the **Duplicates sidebar item**, beside the other outstanding numbers, since a line above a 261-task list is scrolled past. `duplicateGroups()` over 261 open tasks measures **23 ms**, so the 30-second poll carries it.
- **The board says when copies exist.** The Duplicates page worked and was never found — "why duplication?" is asked of the list on screen, not of a sidebar item. The tasks poll now carries the count and one line above the list links straight there. 6 more cases in `duplicates.test.mjs`.
- Reminders reach the in-app notification centre and, when enabled, a browser push. WhatsApp is off by default and even then only messages Dinesh's own chat. `backend/tests/lifecycle.test.mjs` (36 cases, `npm test`) covers the ladder, spacing, duplicates, claiming, completion, reschedule, matching, timezone and quiet hours.

### Work history
- **`task_events`** records the lifecycle as it happens — created, edited, deadline set/changed, reminder created/triggered/snoozed/cancelled, follow-up scheduled/triggered, needs attention, status changed, completed, reopened, archived, note added. Rows are never rewritten, so a deadline moved twice shows both moves. `tasks.original_due_at` keeps the first deadline a task was given.
- **Work History** (`/api/history`) is the permanent record: everything done or archived, searchable by title, description, notes, chat, contact and the original WhatsApp message, filtered by date range, source, priority, chat and on-time/late. Its figures are computed over exactly the rows shown, so the summary always agrees with the list. `GET /history/:id` returns one task's whole timeline.
- **On time or late** compares `completed_at` against the resolved deadline. A task with no deadline reports "no deadline" rather than being called on time.
- **Several at once.** Asked for as *"ek saath select karke delete karne ka option do"*, over a list carrying a hundred rows that were never tasks — a chat's pleasantries, work already given to somebody else, the copies the app made of its own reminders. One row at a time is not a way to clear that; it is a reason to stop opening the list. **Select** in the toolbar turns the done-tick into a picker (the same control, because a row with two checkboxes is a row nobody reads correctly), the whole row becomes the target, and a bar fixed to the bottom of the screen carries *"N selected · Select all · Delete · Cancel"*. `POST /tasks/bulk/archive` and `/bulk/restore` take id lists; an id already gone is skipped rather than failing the batch, and an empty batch is refused. It **archives**, like the single delete — and the undo puts the whole batch back in one request, which matters most here because this is the one action that can take fifty rows off the list at once. 5 cases in `filing.test.mjs`.
- **Allotted work leaves the board.** Asked as *"yaha pe bahut saare allotted task aa rahe he — uska allotted ki tab me dalne ka kya option he"*: half of All Tasks was other people's work, and the thing he actually had to do was somewhere inside it. Work with `assigned_to` set and not yet done is now off the board — the list, the KPI figures, Focus today, the calendar and the rail all read it the same way, so the numbers still agree with the rows shown — and **Task allotted** is where it lives. It is **moved, not dropped**: the reminders, the ladder and the deadline are untouched (it is still his to chase, and the app still nags *him*, never them). And it is not hidden quietly — a line above the list says how many are with somebody, links straight to the page, and **puts them back in one press**; search reaches them wherever you are. Only the *unfinished* half leaves: a finished delegation is just finished work and stays in Completed, which is also what makes the count exact — it is the same number the sidebar badges. The toggle is deliberately not remembered between visits, because a setting left on weeks ago is how a list quietly stops being what you still have to do.
- **And a way to put many there at once.** Per-row handing over already existed (the **Staff** button), which is why the board filled with allotted rows one at a time. **Select** now carries **"Give to…"** beside Delete: one name, typed or picked from the people already on the list, applied to every row picked — fifty rows without opening fifty drawers. It brings a known person's WhatsApp id with the name, so a follow-up written later knows which chat it belongs in, and it sends nobody anything. No bulk endpoint: assigning is a small write and a handful in parallel is milliseconds, where a route would be a second way to do the same thing. 5 cases in `assigning.test.mjs`, including that the board's rule and the sidebar's count are the same rule and that an allotted task is still chased.
- **The folder strip is the same size as the day chips above it.** Asked as *"task folder ko today tom jitni size ka bana do"*. They were tiles — taller, rounder, each count in a pill of its own — and the grid shape laid them in 148px columns, so *SST 4* took the same width as *AUDIT 30 SEP 2026* and nine folders filled two rows of cards. Stacked under All / Today / Tomorrow they read as a second, heavier control rather than the next row of the same one. Now: same padding, same type size, same corner, the count as plain muted figures, and the grid is a **wrap** rather than equal-width columns, so each chip is as wide as its own name — nine folders on one line, the list higher up the page. (A button does not inherit the page's line-height, which alone left them five pixels short of matching.) Names get 20ch, because at 13 *"AUDIT 30 SEP 2026"* was cut to *"AUDIT 30 SE…"*, which names no folder anybody recognises.

Toggle, time, "Fetch now" (build without sending) and "Send now" live on their own sidebar page, **Automation → Law updates**, with the last week's digests folded underneath. - **Verified live on 10 Sep 2026** — the first real digest went out at 10:45 PM with real TaxGuru links (87A rebate on 111A STCG, AGM extension via GNL-1, an ITAT Nagpur ruling). The feeds, the model, the send path and the storage all work in production. **The page renders it as something to read**, not as the WhatsApp message it is: the asterisk markup is parsed back into a heading, labelled rows in reading type, a highlighted "Client ko batao" callout, and the source as a `taxguru.in ↗` link at the end of the line instead of a bare URL mid-sentence. ### Tax & Compliance Law Updates — the records behind the digest
- The digest used to be the whole feature: one block of text a day, stored only so the page could show what was sent. You cannot search a paragraph, mark one line of it reviewed, or find in October the notification you half-remember from September. So **each update is now a row** (`law_updates`) and the digest is *composed from* those rows.
- `backend/src/law-updates.js` — 43 categories in 10 groups (a GST notification and a GST circular are different things to someone looking for one; the groups keep the filter bar to ten buttons). Review workflow (new / reviewed / important / archived, with reviewer and time). Search across title, summary, doc number, category, authority, action and the AI explanation. `composeDigest()` builds the WhatsApp message.
- **Extraction is structured now** (`extractUpdates` in `law-digest.js`, zod + `messages.parse`): category, title, summary, what changed, previous → new position, who it generally applies to, action required, effective date, deadline + **deadline_confirmed**, doc type and number, priority, and a plain-language explanation in the fixed WHAT HAPPENED / WHAT CHANGED / … shape. The prompt's hard rule is that an empty field is correct and a plausible sentence is not.
- **Official vs secondary is read off the domain**, never asked of the model (`classifySource`) — cbic.gov.in is official, taxguru.in is secondary, and the row says which. A model that guesses this wrong turns a news write-up into a confirmed notification.
- **A deadline is only "confirmed" when the article stated it.** Unconfirmed ones are shown, marked, and kept *out* of the digest's deadline list and out of a client message's face.
- **Duplicates**: unique on `source_url`, plus a fingerprint on the doc number (or the first eight words of the title) — the same circular from three feeds is one row.
- **Client message is assembled locally**, not by a second AI call: the facts are in the row, and re-wording a legal fact is a second chance to get it wrong. WhatsApp and email versions, copy button, **no client mapping anywhere**.
- The digest gained an **Urgent** block and a **Deadlines** block. A section whose only update was lifted into Urgent says "upar Urgent me diya hai" rather than "koi naya update nahi" — the small lie that costs a reader trust in the whole message.
- **Day boundaries are the user's, not the server's**: SQLite `date('now','localtime')` reads the machine (UTC on Railway) while rows are stored under the Indian date, so every "today" count between midnight and 05:30 IST answered for yesterday. Now computed in `TIMEZONE`.
- `law_updates` carries a **`module`** column ('tax' | 'legal') so the Legal & Court module is an addition rather than a rewrite. `backend/tests/lawupdates.test.mjs` (20 cases).

### Legal & Court Updates — the second module
- **Deliberately separate from the tax module.** A circular tells a client what to do by a date; a judgment tells the firm where an argument now stands. Own categories (33 in 11 groups: Supreme Court, High Courts, NCLT/NCLAT, ITAT/CESTAT/GSTAT, other forums, corporate & insolvency, commercial & civil, labour, IPR/data/constitutional, legislation, landmark), own feeds (`LEGAL_FEEDS`; LiveLaw, Bar & Bench, SCC Online, TaxGuru judiciary), own digest (`legal_digests`), own claim key (`legal:<day>`), own switch (`legalDigest`, 09:00) and its own sidebar page — **Automation → Legal & court**, beside **Tax & compliance**.
- **Shared underneath**: one `law_updates` table (the `module` column), one review workflow, one search, one component. "Mark reviewed" is the same act whichever list it happens in; duplicating 400 lines of UI to say so would have been the mistake.
- Legal-only columns: court, case_name, case_number, judgment_date, legal_area, bench, petitioner, respondent, act_section, key_issue, decision, principle, implication, **ruling_type** (new precedent / reaffirmed / overruled / larger bench / interim / final / amendment). A tax row leaves them null.
- The digest reads **by forum** and closes on **what moved** (overruled, larger bench, new precedent) rather than on deadlines — a judgment has no filing date to chase.
- **A statute is not a judgment**: for legislation the labels read Authority / Notified on / What it provides, not Court / Judgment date / What the court decided.
- **Never invent a citation.** The prompt's hardest rule: a case number, bench, section or holding the report did not state comes back empty. `ruling_type` is validated against the list, so a value the model made up is dropped. Source link comes from the article, never from the model.
- **Fixed a real dedupe bug found here**: `source_url` was UNIQUE, so a round-up article reporting two judgments silently lost the second. Identity is now the case/document number, with the URL as fallback; the old unique index is dropped at boot.
### Watch list — the sections a practice lives on
- Asked for as *"need sec 138 releted case update"*. A digest is a day's news; a **watch is a standing interest** — Section 138 NI Act (cheque bounce) is most of what an Arth Advisory recovery file turns on, and it matters in March as much as in September.
- A watch is a **saved search with a name**, deliberately: it matches on the text actually recorded (title, summary, doc/case number, court, `act_section`, decision, principle, the AI explanation), through the *same* SQL clause the search box uses — so what a watch flags is exactly what typing the words would have found, and it can be checked. It never asks the model "is this relevant?": a model that guesses that wrong either buries the one judgment that mattered or flags forty that did not.
- Terms are a comma-separated list because the same thing is reported three ways (`section 138` / `cheque dishonour` / `negotiable instruments`), and a watch on one spelling misses the other two. A term under three characters is **refused** — a watch that flags everything is a watch nobody reads.
- **Section 138 is seeded on first boot** (`seedDefaultWatchesOnce`, marker in `meta`), with both spellings of dishonour. Deleting it sticks.
- Its hits get a **👁 block in the digest**, under the watch's own name, so the judgment reaches WhatsApp without anyone searching for it. An update already shown under Urgent is named there rather than printed twice.
- **A real hole this exposed:** the digest names five groups out of eleven, so a cheque-bounce judgment, an NCDRC order or an RBI circular was fetched, summarised, **paid for and then left out of the message entirely**. Anything the named sections don't cover now goes in a **Baaki** block. Two new legal categories as well: *Cheque Bounce / Negotiable Instruments (S.138)* and *Debt Recovery / DRT & SARFAESI*.
- Both modules have their own watches (`law_watches`, unique on `(module, label)`), a chip row above the filters that scopes the list, and `GET/POST/DELETE /watches` on each router. 10 more cases in `lawupdates.test.mjs`.

### A watch goes looking (`law-watch.js`) — filtering is not finding
- **The first morning of the Section 138 watch read `0`, and it was right to.** The legal feeds are general top-story feeds; a cheque-bounce judgment reaches them perhaps once a week, and today's eight judgments were about human rights, EWS certificates and building collapses. A watch that only filters what those feeds happened to bring will read 0 while the practice it names goes on happening. Reported as *"138 not showing properly"*.
- So **a watch carries its own sources and reads them over 30 days**, not the digest's 26 hours: a news search (`news.google.com/rss/search?q="section 138" OR …`) plus `?s=<term>&feed=rss2` on the WordPress sites that answer one (TaxGuru, SCC Online). LiveLaw and Bar & Bench run no search feed, which is what the aggregator is for. Sources are stored per watch and default from its terms; `WATCH_LOOKBACK_DAYS` / `WATCH_MAX_ARTICLES` bound it.
- What it finds goes through the **module's own extractor**, so a judgment found this way is an ordinary row — nothing downstream learns there is a second kind of update.
- **The cost rule is the one that matters.** A month of articles re-read every day is the same summary bought thirty times, so an article already recorded is dropped **before the model is called** (`knownUrls`), and an article whose headline and excerpt never mention the watch's words is dropped too — a search engine answering loosely is not a reason to buy a summary. A day with nothing new costs **nothing at all**: no call, not a cheaper one. Proved in a browser, where Look ran green with no API key present.
- **A `0` is never ambiguous**: every fetch stores what each source did, and the page says *"2 found; TaxGuru search did not answer"*. A quiet month in the courts and three dead sources are different facts.
- **Look now** on each chip (`POST /watches/:id/fetch`), plus a daily sweep on the reminder tick claimed once a day (`watch:<day>`), run before the digests so a find is in this morning's message rather than tomorrow's.
- **An aggregated item links back through the aggregator**, so `saveUpdate` classifies on `publisher_url` (from the feed's `<source url>`) when there is one — otherwise every find would be filed as "news.google.com". `feeds.js` also strips tags either side of the entity decode, because an aggregator escapes the markup in a description and one pass left `<a href=…>` in the stored summary.
- **`.nic.in` is official.** Most high courts publish there, not on gov.in, so `bombayhighcourt.nic.in` was being filed as somebody's write-up — the exact error the classification exists to prevent.
- `backend/tests/lawwatch.test.mjs` (10 cases): the longer window, the term check, the pay-once rule, the publisher classification, that a find is an ordinary row the chip and the digest both see, and that a dead source is reported by name.

- `backend/tests/legal.test.mjs` (13 cases) — the wall between modules, the legal fields, the empty-field rule, the digest shape, one-per-day, and that its spend is measured as `legal_digest`.

### Cost control (after the bill hit ₹175/day)
- The finding: **593 calls in one day, ~3.2k input tokens each, 2-3 WhatsApp lines per call.** 99% of the bill is input tokens, and ~90% of every call was the same preamble — the ~1,900-token system prompt plus 71 business names — re-sent. Not the messages.
- **Prompt caching**: the preamble is now one `system` block with `cache_control: {type:'ephemeral'}`; the business list moved into it (stable), the date and messages stay in the user turn (volatile). Cached reads cost 0.1×.
- **Batching**: quiet window 15s → 30s, ceiling 90s → **240s**. Four minutes, not five, because a cache entry lives 5 minutes from the last call that touched it and a cache *write* costs 1.25× — the ceiling must sit inside the TTL it depends on.
- **Caching does not work on the model in production, and switching is NOT the answer — for a reason that is now measured rather than argued.** Minimum cacheable prefix is not monotonic: `claude-sonnet-5` caches from 1024 tokens, `claude-haiku-4-5` only from **4096**, silently — so on a ~3,200-token preamble nothing caches, which the AI Usage page states from the API's own `cache_read` of zero. I first recommended switching to sonnet-5 and that was wrong, but **the figure I ruled it out with was also wrong**: sonnet-5 is 2× haiku's input rate and **2×** its output rate ($2/$10 against $1/$5), not 10×, and output is only **1.8% of tokens** here, so the output rate barely enters it. What actually decides it: a cache entry lives **five minutes**, and a call that asks for a cache and misses pays **1.25×** — worse than never asking. So the switch pays only above a hit rate of **65%** (`cacheBreakEven` in `pricing.js` derives it from the prices: the rate at which sonnet-5's cached input equals haiku's uncached), and that 65% is the candidate's *best case*, assuming the whole prompt is the repeated part when roughly a third of it is not. Against that, **`cacheReach` measures the hit rate this workload could actually reach** — the share of extractor runs that followed the one before inside five minutes, taken from `api_usage.at`, not from the batching settings, which say what the window allows rather than how often messages arrive. At ~94 runs a day the gaps are ~10 minutes, so the reach is far under the break-even and the switch would *raise* the bill. The page now says both numbers and names the model it is rejecting. **Fewer runs is still the lever that actually works.**
- `api_usage` gained a **`kind`** column (extract / tidy / law_digest) and `costOf` now prices `cache_read` (0.1×) and `cache_write` (1.25×) — leaving them out would have shown a fall in spend that never happened.
- **AI Usage → Where it goes**: per-kind spend, tokens-and-messages per call, and the busiest chats with the tasks each produced (a chat with 420 messages and 2 tasks is the row to block). Per-chat rupees are deliberately *not* shown — a batch mixes chats, so no honest figure exists.
- **"Which messages, from whom?"** — each busiest-chat row opens to show the messages that produced nothing (sender, time, text) with a **Block this chat** button right there, and a **Who is sending them** list names the people behind them. A "0 tasks" figure alone cannot distinguish a group forwarding good-mornings from a client the extractor keeps missing; the messages can.
- `backend/tests/spend.test.mjs` (10 cases) covers the cache marker, that nothing volatile precedes it, the cache pricing and the per-kind split.

### Reliability work after the first outage
The deployed app went down with Railway's "Application failed to respond". Cause: **the whole Chromium profile lived on the data volume**, cache included, growing ~50 MB/minute during a WhatsApp sync with nothing pruning it. A full volume stops SQLite writing; the database opens while modules are still loading, so the process died before the HTTP server was ever bound, ten times over, and Railway gave up.
- **Chromium's cache is off the volume** now (`BROWSER_CACHE_DIR`, bounded at 64 MB) and anything an earlier run left there is deleted at boot. Only the login (IndexedDB, Local Storage, Cookies) stays on the volume.
- **Boot order is inverted.** The HTTP server binds first from nothing but `PORT`; everything else loads after inside a try/catch. A failure now serves "WA Tasks did not start — <reason>" on the URL already open. The health check answers 200 while degraded **on purpose** — a 503 fails the deploy and restores Railway's blank page, which is what this exists to prevent; the body says `ok: false`.
- **WhatsApp and the reminder schedule start independently**, so one failing cannot cancel the other.

### Auth: the lockout was locking out its own user
`requireAuth` counted **every** request without a valid token. The dashboard fires three or four before it has a password to send, so opening the page spent most of the five attempts and one typo locked the address out for fifteen minutes. Now only a *wrong password* counts — a request with no token at all is the dashboard on first load, not a guess, and an attacker still has exactly five tries. Covered by `backend/tests/auth.test.mjs` (9 cases).
- A locked-out dashboard used to say "Something went wrong" because the banner discarded the message; it now shows what the server said, including the wait.
- **`GET /api/auth-state`** is unauthenticated and reports whether a password is required at all. With none set, the dashboard shows a standing banner saying anyone with the link can read and change the tasks. It leaks nothing: without a password every task was already readable.
- **Verified end to end**, which had been outstanding for a long time: with `DASHBOARD_PASSWORD` set every `/api/*` route 401s without a valid token, the login screen appears, a wrong password is rejected, the right one gets in, and five wrong ones return 429 with `retryAfterSeconds`.
- **Then he set the password for the first time and could not get in.** Reported as *"login nahi ho raha he"*. The API, the login screen and the token round trip were all correct — driven in a browser, they worked first time. The cause was a **space around the variable**: a password pasted into Railway's box very easily carries a trailing space or a newline, and the box shows neither. `DASHBOARD_PASSWORD` was read as `process.env.DASHBOARD_PASSWORD || ''`, untrimmed.
- **It is far worse than being hard to type: such a password can never be sent at all.** HTTP strips leading and trailing whitespace from a header value, so a password ending in a space **cannot travel in an `Authorization` header** — the correct password is refused, the fifth refusal locks the address out for fifteen minutes, and nothing anywhere says why. Reproduced exactly: with the variable set to `'MySecret123! '`, both the password as typed *and* the password with the space were refused, and five attempts returned `429 retryAfterSeconds: 900`.
- Both ends are trimmed now — the configured password in `config.js` and the submitted token in `requireAuth` — so invisible whitespace can never be the thing standing between him and his own task list. Trimming costs a password whose meaning depends on characters nobody can see, which is a password nobody could type reliably anyway. **The repair is not silent**: when the raw variable had whitespace the boot log says so and says to fix it, because a variable quietly patched at read time stays wrong for the next person who copies it. Verified with the same bad variable: login now succeeds in a real browser. 3 more cases in `auth.test.mjs`, the last of which runs `config.js` in a child process with the padding a paste actually leaves behind.

### Checklists, dependencies, templates, files, low-confidence holds
The five items the master prompt listed and earlier phases deferred. In each case the reminder engine decided the design.
- **Checklists** (`subtasks` table) — steps inside a task, progress on the row. Ticking every box **does not** complete the parent: completion cancels the whole ladder and writes to the permanent record, too much for a side effect. The panel says every item is ticked and leaves finishing explicit.
- **Dependencies** (`task_dependencies`) — a blocked task **keeps** its deadline and reminders; what changes is that the reminder and the row name the blocker. Going quiet on a deadline is how things get forgotten. Completing a blocker reports only what it genuinely freed (nothing else still waiting). Cycles are refused at write time via a walk of the chain.
- **Templates** (`task_templates`) — name, title, priority, `due_in_days`/`due_time`, and a checklist. Using one produces an **ordinary task**, so nothing downstream sees a second kind of task. The deadline resolves on the user's calendar, not the server's.
- **Attachments** (`attachments` + files under `DATA_DIR/attachments`) — 10 MB per file, 200 MB total, remaining space shown in the UI. Deliberately bounded: this is the volume whose filling up once stopped the service booting. Uploaded filenames are display-only (`safe-name.js`); bytes go under a random name. Orphans from a crash between write and insert are pruned at boot. Upload is a raw body, not multipart — one file per request needs no boundary parsing and no new dependency.
- **Low-confidence holds** — the extractor now returns `confidence`, and `low` sets `needs_confirmation`. Such a task is created but **not chased**: `planTask` refuses to build a ladder, the digest query excludes it, and the briefing filters it out. It waits in the dashboard's "Is this a task?" panel with its original message. Confirming enters it into the ladder; rejecting **archives** it. The wording everywhere states this is the model's own report, not a measurement.
- `backend/tests/extras.test.mjs` (24 cases) covers all five, including that a checklist never completes its parent, that a blocked task still gets reminders, and that an unconfirmed task is never scheduled.

### Added since the original spec
- **Deployment config** — `wa-task-assistant/Dockerfile` (bundles Chromium for `whatsapp-web.js`, builds the frontend) plus `railway.json`. The Dockerfile sits at the build-context root so Railway auto-detects it, and carries **no `VOLUME` instruction** — Railway rejects it outright (`docker VOLUME ... is not supported, use Railway Volumes`) and the build dies in ~2s at "Build image". Attach a Railway volume at `/data` instead. `railway.json` also names no `dockerfilePath`, since that resolves against the repo root rather than the service root directory. - **Dashboard auth** — a single shared secret via `DASHBOARD_PASSWORD`. Every `/api/*` route requires `Authorization: Bearer <it>`; `/healthz` stays open. Unset means no auth, which is fine locally but not on a public URL.

An **Install** button appears where the browser offers one; iOS gets the Add-to-Home-Screen instruction instead, because it never offers the prompt.

### Which build is running — because "still not working" and "not deployed yet" look identical
Three reports running were answered by a fix that was already written, verified in a browser and pushed, and the screenshot could not say whether the code on his screen was that code. That ambiguity is the bug: it costs a round trip every time and sends the next fix looking in the wrong place.
- The status panel carries a **build line, always visible** — not behind the diagnostics block, which only opens when the session is down, so the one fact that says "this is the new code" used to be hidden exactly when everything looked fine and was not.
- It reports the host's commit (`RAILWAY_GIT_COMMIT_SHA`), and — because that is null wherever the host does not set it, which is exactly when it is needed — **the dashboard bundle the server is actually handing out**. Vite names the bundle after a hash of its own contents, so the name *is* the version: if it matches what the browser loaded (DevTools → Network), the screen really is running that code. Nothing is ever written by hand; a version number that can drift from what is running is worse than none.
- **The service worker could serve a deploy stale for ever.** `activate` deletes every cache whose name is not the current one, and the name was a fixed `wa-tasks-v1` — so that sweep deleted nothing, ever. Navigations are network-first, so the page itself stayed fresh, but every hashed asset a browser had fetched was kept indefinitely. The cache name moves with the release now.
- `backend/tests/build-stamp.test.mjs` (4 cases): the stamp names a file that really is in `public/assets`, no literal sha is ever hard-coded, the line is not gated on a healthy connection, and the cache name is not the fixed one.

### Backups — the audit's one finding with nothing standing behind it
- Every task, message, lead and the whole history lived in **one SQLite file on one Railway volume, with nothing anywhere copying it.** A deleted volume, a corrupted write or a mistyped action in the Railway console destroyed the lot with no way back. `makeBackup()` in `backups.js` takes a nightly copy and keeps the last 7 (`BACKUP_KEEP`).
- **`VACUUM INTO`, never a file copy.** It asks SQLite for a consistent, compacted copy while the app carries on. A filesystem copy of a live WAL database is exactly the thing that yields a backup which restores to nothing — so the test opens the copy and reads the rows back rather than checking the file exists.
- **It must never fill the disk, because that is how this app went down the first time.** The volume filling stopped SQLite writing, the process died before the HTTP server was bound and Railway gave up after ten restarts. So old copies are pruned **before** a new one is written (keep+1 copies existing even for a moment is the moment a tight volume has nothing left), and a snapshot that would not leave a 200 MB margin free is **refused and reported** rather than attempted. `makeBackup` returns `{ok:false, reason}` rather than throwing — the same pass sends reminders, and a disk too full to copy is exactly when those matter most.
- **It rides the reminder tick, not its own cron**, claimed once a day under `backup:<day>` like the briefing. The tick runs every few minutes, so a machine asleep or redeploying at the scheduled minute still takes the day's copy the moment it is back; a once-a-day cron would simply have missed it.
- **A copy beside the database is not a backup against losing the volume**, and the panel says exactly that instead of showing a green tick. `offVolumeCopy` is a field, permanently false. **Download** is the loudest control on the panel because it is the only action there that survives the failure the panel exists for; it goes through `fetch` with the bearer token, since a plain link sends no Authorization header.
- **A real bug the live test caught and a unit test would not have.** `listBackups` sorted by name, and a second copy taken the same day carries the clock: `tasks-2026-09-15-044502.db` sorts **before** `tasks-2026-09-15.db` because `-` precedes `.`. So the day's *older* copy was reported as the latest and the download button handed back a file from before the morning's work — the exact failure the feature exists to prevent, wearing a green tick. Sorted by **write time** now, with the name only as a tie-break.
- The download route matches the filename against a fixed pattern rather than sanitising it, so nothing outside the backup directory is addressable however the path is spelled — verified live against `../tasks.db`, `..%2F..%2Fetc%2Fpasswd` and `tasks.db`, all 404. `backend/tests/backups.test.mjs` (11 cases).
- Verified end to end on a running server: a copy taken through the API, downloaded over HTTP, re-opened read-only with 1 row, Gujarati intact and `integrity_check = ok`.

### The list by month, and the cap that used to bite in silence
- Asked as *"itna karo ki usme month wise dikhe — month complete ho aur us month ke task pending he to us month ki tab me dikhe"*. A strip of month chips sits above the list, under the day chips and the same size as them, and pressing one scopes the board to that month.
- **A month a task belongs to is its DEADLINE's month, falling back to when it arrived** (`taskMonth` in `lib/task.js`). Work due on 20 October is October's work whenever the message came in; only a task with no deadline at all has nothing better to go on. `due_date` is already a plain local day, so no timezone conversion can go wrong on it.
- **The rule he actually asked for lives in `monthsFor`: a finished month keeps its chip for exactly as long as it still has work owed.** September's audit, still open in October, does not quietly become October's problem and does not disappear because September ended — it stays under September with its own count until it is done. A past month everything is finished in loses its chip, because there is nothing left to chase and its work is in Completed. The current month is always shown even when empty: a row that loses today's chip on a quiet morning reads as broken.
- **The counts come from the rows the board is already showing.** The big filter memo was split: `monthPool` applies view, folder, delegation and the rest, and `visible` applies the month scope **after** it. That ordering is the whole reason the strip can be trusted — a chip reading 6 opens a list of 6, and picking September does not collapse every other chip to zero. Deriving the counts from a second query would eventually mean a chip and its list disagreeing, and then neither would be believed. Search ignores the month scope entirely: if you went looking for something you want to find it.
- **The 500-row cap was the audit's High finding and it said nothing when it bit.** `listTasks` capped at 500 with no signal, on a board carrying ~280 tasks — and because the dashboard fetches the whole list once and slices it client-side, a cap that bites does not just hide tasks, it makes the month strip and the folder counts wrong with it. The cap is 2,000 now (hard limit 5,000), and **the true total travels beside the rows** (`countTasks`, `total`, `truncated` on the tasks route) so the day it is ever reached the page can say so rather than silently dropping the rest. `taskScope()` is shared by the list and the count, so the two can never be counting different things.
- `backend/tests/months.test.mjs` (13 cases) pins both halves of his rule — that a finished month keeps its chip while work is owed, and loses it when none is — plus the deadline-over-arrival rule and that the chip's figure equals the list it opens. Two cases in `assigning.test.mjs` were sliced from `const visible =`; they now read the whole chain, because the rule they check moved with the predicate while staying in the same chain.
- Verified in a browser across three months: *All months 6 · Oct 2 · Sep 3 · Aug 1●* — August over, one task still owed, chip kept and dotted; pressing Sep gave exactly the 3 rows its chip promised; no sideways scroll at 390px.

### An unlinked device could never come back — the trap the QR-over-HTTP feature was meant to prevent
- Seen live, from the dashboard: **`WhatsApp: Disconnected`**, *Starts so far 162*, a saved login of **1,246 kB** on the volume, and a connection log reading `authenticated` four times then `OPENING → PAIRING → `**`UNPAIRED`**` → disconnected`. The device had been removed from the phone, so the stored login was dead.
- **The `disconnected` handler only wrote the reason down.** So the dead session stayed on the volume, no `qr` event ever fired again, and every restart authenticated with the same dead login and was unpaired again — 162 times. With no shell access there was no way back, which is exactly the situation serving the QR over HTTP exists to prevent. There was no logout, relink or reset path anywhere in the codebase; the only `destroy()` was in `shutdown()`.
- **`relink()` clears the login and starts again**, so a fresh QR appears. **Destroy before delete**: Chromium holds files inside the profile while it runs, and removing the directory underneath it leaves a half-deleted profile that fails to open — which would turn "scan again" into "the app will not start". A 1.5s pause covers the handles it releases after `destroy()` resolves, and `relinking` stops two of them running at once, since each starts a Chromium.
- **The opposite mistake is the one to fear, so `isUnlinked` matches `UNPAIRED|LOGOUT` and deliberately nothing else.** `NAVIGATION`, `CONFLICT`, `TIMEOUT` and a bare disconnect all heal themselves and leave the login valid; throwing it away because the wifi dropped for a moment would cost a trip to the phone for nothing.
- **A button as well as the automatic path**, because a session that died while the app was *down* never announces itself — which is precisely this case. It sits in the connection panel only while the connection is not healthy, and asks first, saying what it costs (*"You will have to scan it from your phone"*) and what it does not touch (tasks, history, notes).
- Verified live: a 3 MB stale session on the volume, the button pressed, the dead login gone, a fresh profile created by the restart, and the task data untouched. `backend/tests/relink.test.mjs` (8 cases) — most of them pinning which reasons must **not** clear the session.
- **And then the scan itself failed: *"phone me Try again later hi aa raha he"*.** Not the library (1.34.7, current) and not a stale code (the dashboard already polls every 5s while waiting). **`whatsapp-web.js` defaults `qrMaxRetries` to `0`, which means UNLIMITED, and this app never set it.** So an unpaired client asks WhatsApp for a fresh pairing code roughly every 20 seconds, for ever — sitting disconnected for **seven hours**, as it was, that is **over a thousand requests to link one account**, every one of them while nobody was holding a phone. WhatsApp answers that by throttling, which is the *"Try again later"* on the phone — and then the one scan actually being watched fails too.
- **His phone then showed why the link died in the first place.** Linked devices → the entry he had renamed by hand to **"WA TASK"**, reported as *"Google Chrome (Mac OS)"*, **last active 22 July** — eight weeks — under WhatsApp's own banner: *"Logging out today. Linked devices automatically log out if they haven't been active in a while."* Two of the three problems there are the app's.
- **It linked under a name indistinguishable from any browser left signed in.** `whatsapp-web.js` takes `deviceName` / `browserName` and the app set neither, so its row looked like an ordinary Chrome session — on a list capped at **four devices**, where telling a dead row from a live one decides whether you free a slot or unlink the wrong thing. He had already renamed it by hand, which is the tell. Set to **`WA Tasks`** now.
- **"Disconnected" read the same after a minute and after two months.** `last_ready_at` is written to `meta` at the moment the client actually becomes ready — written, not derived, because the app restarts on every deploy — and the panel now says *"This link last worked 55 days ago. WhatsApp logs a linked device out once it has been idle for a while…"*. Silent under two days, because a blip is not a rotting link and a warning shown on every brief disconnect stops being read.
- **The QR then appeared correctly and the phone still said "Try again later"** — so the refusal was already in force on the account, and something was still feeding it. **A client that starts unlinked begins requesting pairing codes at once**, and this app restarts on every deploy: an ordinary day of work spends scores of pairing requests nobody ever saw, which is what keeps the refusal standing for the one scan that *is* being watched. So **with no saved login the client is not started at all** — `startWhatsApp({ force })` rests in a `needs_link` state until the button is pressed. A saved login still reconnects by itself, so a working install loses nothing. Verified separately that the QR path itself is sound end to end: a real pairing string rendered, served and decoded in a browser at 240×240, with the CSP's `img-src data:` allowing it.
- Bounded to **12 codes (~4 minutes)** via `QR_MAX_RETRIES`: long enough to fetch a phone and open Linked devices, short enough that an app nobody is looking at stops asking. Linking is a deliberate act and should happen when a person is ready for it.
- When it gives up, the library emits `disconnected` with *"Max qrcode retries reached"*. That is a **resting state, never a reason to clear the login** — losing the session because nobody scanned for four minutes would be a far worse bug than the one being fixed — so it is caught *before* the unlink branch and returns. The panel then says so in the user's own words (it names *"Try again later"*), tells him to open **Linked devices on the phone first, camera ready**, and offers **Show a new QR code** — `showQr()`, which restarts the client but **touches nothing on disk**, so it is the safe one of the two buttons. 5 more cases in `relink.test.mjs`.

## Known constraints / things to respect
- `whatsapp-web.js` is an unofficial library (automates a WhatsApp Web session via Puppeteer/Chromium). It's the standard approach for reading a personal account programmatically, but keep usage passive (reading + occasional self-reminders) — no mass-sending or scraping other people's data — to avoid any account risk.
- Single WhatsApp Business number used across all of Dinesh's ventures is `9909993565` — this personal-WhatsApp task assistant is a separate, distinct thing from that number/setup.
- Dashboard auth is one shared secret (`DASHBOARD_PASSWORD`), which suits a single user. It is not multi-user auth, and messages/tasks sit unencrypted in SQLite. Leaving it unset disables auth entirely — only do that locally.

## Open decisions / not built
- **Scaling to other users is a dead end and Dinesh has accepted that.** Each user needs their own Chromium (~500 MB idle, measured), so 10 users is ~10 GB RAM, and `whatsapp-web.js` commercially breaches WhatsApp's terms. The ambient behaviour that makes this worth having is exactly what stops it being a product. A Business API version would scale legally but loses personal-chat reading and lands in a crowded market (Any.do, Zuno, WapTask, Higgle all ship the "message a bot" model already).
- **Voice-note capture** — probably the highest-value unbuilt feature for his chats. Deliberately not started: the Anthropic API does not take audio, so it needs a separate speech-to-text service chosen and paid for (Whisper, Google, Sarvam) for Gujarati/Hindi. Building it without a key would mean shipping code that has never run.
- **Weekly summary, CSV export, subtasks, dependencies, templates, attachments and low-confidence confirmation are all built** — see the sections above. What remains unbuilt from the master prompt is voice capture only.
- **Encryption at rest** for the session file and SQLite — deferred, not refused.
